What this run actually showed

5/10 → 6/10

Correct tasks with the same two-attempt evaluation budget, before and after RL.

0/3 → 1/3

Official held-out tasks solved. The additional success was MinGPT GELU.

16 updates

Four recorded epochs, 64 training episodes, and nonzero finite gradient norms at every update.

A modest observed improvement, not broad proof. Training-task correctness stayed 3/4 and reserved-transfer correctness stayed 2/3. First-turn correctness stayed 5/10 overall. The new success appeared during refinement on turn two.

The base model supplied a GELU module with an incompatible constructor on both attempts. After training, the model first hit an unsupported tl.tanh call, then replaced the computation with an erf-based Triton implementation that passed the evaluator. Its measured runtime was approximately 0.184 ms versus 1.624 ms for eager PyTorch on H100, or 8.83× for this one task.

The successful kernel also passed five additional fresh signed-input seeds at the original shape; maximum absolute error was 0.0004735. The reference uses a tanh approximation to GELU; the generated erf form agrees within the benchmark tolerance, not bit for bit. Validation record

System architecture

The language model and kernel evaluator use separate physical GPUs. The server coordinates OpenEnv sessions, while each submitted kernel runs in a fresh subprocess.

Both devices were verified NVIDIA H100 80GB HBM3. They shared a Modal container, with disjoint GPU assignments. This isolates training load from timing, but does not provide a separate container failure boundary. The published dashboard reads a saved snapshot and requires no GPU.

One training step, end to end

01 / RESETChoose one training task and reveal its PyTorch reference.
02 / GENERATESample four independent kernel-writing episodes.
03 / EXECUTEEvaluate each submitted module on the dedicated GPU.
04 / REFINE ↻Return errors or timings; allow one more attempt.
05 / LEARNCompare four episode returns and update LoRA weights.
06 / RECORDSave traces; checkpoint at steps 8 and 16.

Each episode contains at most two model-generated submissions. After the first submission, the model sees compile/runtime errors, numerical mismatches, or speed measurements and can revise the entire module. The trainer joins the two model turns and the environment feedback into one sequence.

task prompt → model tokens → GPU feedback → model tokens
                 train         mask out       train

episode return G = reward₁ + 0.4 × reward₂
group = four trajectories for the same task
advantage ≈ (G − group mean) / group standard deviation
optimizer update → next step uses the updated policy

Only model-generated tokens contribute to the loss. Feedback tokens are marked with an environment mask of zero. The pilot uses episode-level GRPO advantages across the joined trajectory; it does not implement turn-level TRLOO or Kevin's full turn-level credit-assignment procedure.

The reward policy

Correctness is a strict gate. A source rejection, compilation failure, runtime error, timeout, or numerically wrong output receives zero reward in this run. Partial-credit rewards were disabled.

r = 0.3 + 2.7 × min(tmin / tkernel, 1)

t_min is an optimistic hardware roofline lower bound, based on estimated work/data movement and GPU peak throughput. A faster correct kernel receives a larger share of the maximum reward of 3.0. This does not require beating PyTorch.

Roofline share: 50%Step reward: 1.650Incorrect output always → 0

For example, an episode with a failed first attempt and a correct second attempt earning 2.7 receives G = 0 + 0.4 × 2.7 = 1.08. This rewards recovery while still favoring a correct first attempt. The return, not a PyTorch-relative leaderboard score, is the reward function supplied to GRPO.

The environment has a fallback for unknown rooflines: 0.3 + clip(log₂(speedup), −0.2, 3.0) for correct kernels with positive measured speedup. This H100 pilot used the roofline mode. The floor is an estimate, not a claim that every operation can reach peak hardware efficiency.

What has to pass before a reward is trusted

Source and execution checks

Require custom Triton or CUDA work; block known host-side PyTorch fallbacks, prohibited imports and evaluator tampering. Run candidates in fresh subprocesses, with timeouts and separate compilation caches.

Numerical checks

Compare against the trusted reference across five hidden input seeds. Check outputs, input mutation and aliasing. Task-specific adversarial inputs cover signed activation inputs and normalization failure modes where implemented.

Timing checks

Synchronize and benchmark on the dedicated GPU. Serialize timing work. Reject timings below 0.8× the estimated roofline floor and flag extreme speedups for inspection.

The current evaluator passed 116 tests on a real L40S GPU, including real Triton/CUDA execution, rejection cases, timeouts and timing checks. The trainer passed a separate mock-server integration check. These tests support the pipeline's operation; they do not prove that all possible generated programs are safe or semantically correct.

The newly solved GELU kernel then passed an additional replay at its original shape with five new seeds and signed inputs in [−32, 32]. This check occurred after the frozen comparison; its results were not used for more training.

Why this approach can work

Execution provides a concrete target

The GPU tells the model whether its code compiles, computes the expected result and runs efficiently. The signal is grounded in program behavior rather than the style of a plausible-looking answer.

Variation creates a learning signal

For a given task, GRPO compares sampled trajectories. Higher-return attempts receive positive relative advantage and lower-return attempts receive negative relative advantage. Updates can increase the probability of successful code.

Feedback makes repair observable

Multiple turns expose both an error and a repair attempt in the same episode. The observed new GELU success came from fixing a compile failure on the second turn.

There is also a practical prerequisite: the starting policy must occasionally produce reward-bearing solutions. This model solved three of the four training tasks in the greedy baseline and also sampled valid Tanh code during training, so this pilot could begin with RL without a separate SFT/RFT warm-up.

What was verified: all 16 recorded gradient norms were finite and nonzero, the adapter was saved and merged into 196 base tensors, and a freshly loaded saved model generated one additional correct held-out kernel. None of these observations guarantees that longer training will continue to improve the model.

How to interpret the result

  • Small evidence: one training seed, ten evaluation tasks and one greedy episode per task. A one-task gain is not a statistically robust generalization result.
  • Related families: activations appear in both training and evaluation. This is held-out-task evaluation, not unseen-family generalization; public pretraining contamination is not ruled out.
  • Refinement gain: overall first-turn correctness stayed 50%. Best-of-two correctness rose to 60%. The additional success is in feedback-conditioned generation.
  • Speed interpretation: existing solved kernels remained approximately unchanged in runtime. The 8.83× figure belongs to the newly solved GELU task, not the whole model or the whole benchmark.
  • Reward noise: groups of already-correct kernels can differ mainly through timing noise. Nonzero gradients are not proof that every update is useful.
  • Method distinction: this is a small episode-level GRPO pilot. It does not reproduce CUDA Agent's full staged actor–critic PPO, implement TRLOO, or establish equivalence to any cited paper's results.

Research references and what we borrowed

  • Kevin: iterative execution feedback, discounted returns and conservative optimization/clipping.
  • Dr. Kernel: cautions about multi-turn advantage estimation, lazy optimization and trustworthy speed objectives.
  • CUDA Agent: staged training and reliable execution checks; the full training recipe was not reproduced.
  • CUDA-L1: speed-oriented learning and the need to guard against timing exploits.
  • TritonRL: layered verification and anti-cheating controls.
  • KernelLLM: supervised kernel-generation context; this pilot used no SFT phase.
  • TRL GRPO documentation: trainer, custom rollout integration and optimization settings.
