Next stage: the larger campaign

The new $100 budget supports two independent 7B training seeds, broader fixed evaluation, stricter validation and live GPU/optimizer traces. During preflight, a missing Modal module caused startup crash loops. The failing apps were stopped, image construction was restricted to the local launcher, and CPU startup checks were added. The corrected GPU preflight passed 122 tests. The first larger allocation then stopped with 112 WebSocket handshake errors and zero optimizer updates. Its artifacts were retained. The replacement uses the successful pilot’s two-H100 localhost layout, removes region pinning and its surcharge, and checks a real GPU submission before model loading. These are infrastructure fixes; no new learning gain is claimed.

Useful work, with avoidable spending

The earlier runs helped build a functioning training and evaluation system. They produced limited evidence of better kernel generation. Some expensive launches happened before evaluator correctness and a usable learning signal had been established.

Keep

Evaluator fixes, numerical counterexamples, GPU isolation, execution logs, working rollouts and verified checkpoint reloads.

Qualify

Small correctness gains, inference throughput benchmarks and preliminary validation wins. Each answers a narrower question than broad model improvement.

Do not count as clean evidence

Scores from the flawed evaluator, successful loading alone, nonzero gradients alone, and unexecuted training plans.

Separate experiments, not one learning curve. Models, tasks, sampling budgets, hardware and evaluator versions changed. Their pass rates cannot be compared directly or added together.

The experiment timeline

Early runs · recorded 17 October 2026USEFUL INFRASTRUCTURE

Make real GPU execution work

Baselines and smoke runs exposed Triton source-loading failures, missing CUDA build dependencies, tokenizer/processor incompatibilities, false source rejections and a GPU-lock deadlock. Local mock tests had missed these failures.

Value: a working OpenEnv → compiler → GPU → feedback loop, with tracing to locate failures.

Lesson: check the complete path on a small job before reserving many GPUs. Argument-parsing and startup failures also created avoidable overhead.

17 October · original Qwen3.5-9B pilot and later auditSCORES NOT VALIDATED CORRECTNESS

A promising score hid evaluator defects

The old evaluator reported 7/80 → 10/80 correct episodes. Task coverage stayed 5/20 and faster-than-PyTorch episodes stayed 3/80. Truncated turns increased from 37/320 to 58/320.

A global absolute tolerance could accept all-zero Softmax output. Saved accepted candidates included incorrect normalization and a slice-based Frobenius calculation with host-side arithmetic.

Verdict: this increase is not a clean model-improvement result and should not justify more training spend.

The audit used saved code and mathematical analysis. Subsequent GPU controls tested the corrected verifier; historical scores were not comprehensively re-scored.

17 October · evaluator corrections and GPU controlsHIGH-VALUE CORRECTION

Make the reward harder to fool

Reference-scaled checks, normalization invariants, host-arithmetic guards and adversarial inputs addressed concrete false positives. A smoke run also showed why positive-only activation inputs were insufficient: a copy kernel could pass without implementing the activation.

Scoped GPU controls tested valid implementations against deliberately wrong zero, copy, stride and normalization implementations.

Value: a stronger correctness gate before an output could earn speed reward.

Later audits still found gaps for Max, Min and HingeLoss. These controls are scoped evidence, not a guarantee that every generated program is correctly judged.

17 October · corrected 9B pilotSMALL POSITIVE SIGNAL

Limited evidence of actual learning

A 12-update pilot observed GELU validation changing 0/4 → 1/4 correct-and-faster. Checkpoint 8 was selected using that validation, so this was not an independent test.

A separate paired evaluation reported 0/36 → 2/36 correct episodes, including one faster result. Both successes were matmul; seven other tasks remained unsuccessful.

Verdict: a small observed gain, with verified adapter persistence. Broad improvement was not established.

17–18 October · 27B, quantization and inference workENGINEERING EVIDENCE

A larger model added runtime complexity

The 27B path explored FP8/NF4 execution, behavior-policy probabilities, caching, batching, speculative decoding and saved-adapter integrity. Some attempts stopped before any optimizer update.

One batching benchmark measured 3.04× raw throughput but failed its predeclared quality screen on a tiny sample. A separate speculative-decoding comparison measured 1.59× throughput. These factors came from separate comparisons and must not be multiplied.

Value: measured execution tradeoffs and persistence checks. Faster generation did not establish better kernels or validate every rollout/training policy combination.

Avoidable overhead: exploratory ESS and weight-concentration screens were incorrectly promoted to fatal assertions. Failing them was not proof that the training objective was invalid.

18 October · RL continuation and separate SFT forkNO DEMONSTRATED GENERATED GAIN

Real updates did not improve the small comparison

The RL continuation reached step 4. A separate SFT fork trained for two steps on two verified Matmul examples. Save/reload and frozen-base checks passed.

The generated comparison scored 1/2 correct for shared step 1, RL step 4 and SFT alike. Softmax runtimes were effectively identical, around 8.775 ms. All three LogSoftmax outputs shared an accumulation bug.

Verdict: useful persistence and negative-result evidence; no demonstrated capability gain. Shared step 1 was already trained, not a pristine base.

A tiny teacher-forced NLL change did not prove better generated kernels. A subsequent larger adaptation plan remained conditional and unexecuted at the recorded handoff.

19 October · completed OpenEnv proof runMODEST OBSERVED IMPROVEMENT

Return to a smaller, matched experiment

A pristine Qwen2.5-Coder-7B-Instruct received 16 GRPO LoRA updates on four training tasks, with strict correctness gating and two attempts per episode. A matched before/after evaluation used ten fixed tasks.

The additional GELU success came on turn two after compile feedback and passed an independent signed-input replay. First-turn correctness stayed 5/10; runtimes on the already-solved set were essentially unchanged.

Verdict: the framework ran end to end and the saved model generated one additional correct held-out kernel. One seed and ten related-family tasks remain weak evidence of generalization.
